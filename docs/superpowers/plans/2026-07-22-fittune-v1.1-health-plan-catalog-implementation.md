# FitTune v1.1 Health Sync, Plan Editing, and Exercise Catalog Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship FitTune v1.1.0 (build 11) with automatic HealthKit updates, a grouped drag-and-drop plan editor, a full-screen explainable exercise replacement flow, and an expanded, consistently classified exercise catalog.

**Architecture:** Keep the current Codable/UserDefaults snapshot store and add schema-13-compatible fields with decoding defaults. Put catalog, replacement scoring, plan mutations, and health aggregation in platform-independent model/engine files covered by Swift Package tests. Keep HealthKit, WatchConnectivity, and SwiftUI adapters thin; they translate platform events into tested core reducers and AppStore commands. Preserve immutable workout-start snapshots while active-workout edits mutate only the live draft unless the user explicitly saves them back to the source plan.

**Tech Stack:** Swift 6, SwiftUI, Observation, HealthKit, WatchConnectivity, CoreBluetooth, Codable snapshot persistence, XCTest, Swift Package Manager, Xcode iOS/watchOS targets.

## Global Constraints

- All calculated health and energy values must retain source, sample time, synchronization state, and confidence. Health permission or sensor absence reduces confidence and never blocks training.
- Apple Watch or Bluetooth may occupy the single live sensor slot. Huawei Health data is delayed HealthKit import and never occupies that slot.
- Daily all-day HealthKit active energy is authoritative when available. Workout and walking figures explain its composition and must not be added to it a second time.
- Reordering, replacement, fatigue, injury, and equipment warnings are advisory. The app must not silently remove sets, reorder exercises, or end an exercise/training session.
- Completed active-workout exercises and the current exercise after its first recorded set are immutable. Unstarted exercises remain editable.
- `PlanSnapshot` created at workout start remains immutable. Live edits are recorded through `WorkoutChangeEvent`; saving to future sessions requires an explicit user action.
- Every new Codable property must decode old v0.6/v1.0 snapshots safely. Schema migrates from 12 to 13 exactly once.
- Update `Package.swift` and `FitTune.xcodeproj/project.pbxproj` whenever a new source or test file is introduced.

- [ ] **Step 3: Implement reliable phone-to-Watch workout start**

On iPhone workout start, `WatchWorkoutBridge` sends a session-scoped start command and waits for a Watch acknowledgment. Use `sendMessage` while reachable and application context/user info as idempotent fallback. The Watch manager treats duplicate start commands for the same session as no-ops and rejects a different active session until the current one ends.

Each Watch metric packet includes session ID, monotonic sequence, timestamp, source, heart rate, cumulative active energy, and modality-specific cumulative metrics. `WatchMetricMerge` rejects wrong-session, duplicate, out-of-order, implausible, and stale packets. The phone resumes estimate mode with an explicit reason when Watch data stops, then accepts valid reconnection without resetting cumulative totals.

- [ ] **Step 4: Enforce the live-source arbitration rule**

`LiveSensorCoordinator` grants the live slot to one of Apple Watch or Bluetooth. Connecting one disconnects or declines the other with a visible explanation. Huawei/HealthKit post-sync imports bypass this live-source slot and are merged later by workout/time/source identifiers.

Use live HR conservatively: it may extend rest, prevent an aggressive increase, or warn on abnormal state; it must not independently increase next-set weight.
