# FitTune 2.0 架构、易用性与综合运动设计

日期：2026-07-31

## 1. 目标与版本边界

FitTune 2.0.0 是一次兼顾稳定性、运行流畅度、真实训练易用性和综合运动记录的大版本升级。版本号统一更新为 `2.0.0`，构建号更新为 `20`，本地数据 schema 更新为 `16`。覆盖安装必须保留 1.x 的个人资料、计划、力量记录、有氧记录、恢复记录、收藏、自定义动作和未完成训练草稿。

本版本交付以下结果：

1. 降低实时心率、定位和计步数据对主线程、内存和持久化的压力。
2. 将力量训练和有氧训练的唯一主要操作固定在屏幕底部，降低漏点“开始/完成”的概率。
3. 修正当日恢复输入与实际训练算法输入不一致的问题。
4. 将实时有氧与事后补录明确分开，并为实时有氧增加暂停/继续。
5. 新增独立“运动”板块，支持羽毛球、乒乓球、足球、攀岩、徒步、登山和越野跑的实时记录、降级估算、训练总结与历史详情。
6. 将上述记录纳入统一历史、搜索、删除/恢复、导出和今日能量去重体系。
7. 保留单一实时心率来源原则：Apple Watch 或标准蓝牙心率设备同时只能选择一个；iPhone 定位/计步是运动环境传感器，不占用心率来源槽位；华为健康只作为事后同步来源。

FitTune 仍不是医疗器械，不诊断伤病、心血管风险、高原反应或恢复完成度。所有训练效果、能量和恢复时间均显示来源、可信度和合理区间。

## 2. 已审计的主要问题

### 2.1 性能和架构

- `AppStore` 同时承担全局状态、训练状态机、查询、导入、迁移和持久化，实时数据路径最终都会触及同一个大对象。
- 有氧当前每个心率、定位或计步样本都会同步编码并写入完整 `AppSnapshot`；随着样本和历史增长，训练期间会出现越来越多主线程工作。
- 有氧追加样本使用线性查重，页面和 Live Activity 又反复遍历样本数组寻找最新步频。
- Live Activity 可能同时由实时样本变化和 draft `updatedAt` 变化触发，产生重复更新。
- 所有业务数据保存在单个 UserDefaults blob 中；数据增长会拖慢冷启动，主数据损坏时也没有 last-known-good 回退。
- 今日能量、趋势和历史搜索等派生结果在 SwiftUI 重绘时反复全量计算。

### 2.2 真实训练易用性

- 今天页的主要“开始训练”动作位置较深；快速开训需要滚动和多次判断。
- 用户刚调整的睡眠、酸痛、压力和动力只存在页面草稿时，训练可能仍采用上一次 `RecoveryCheckIn`。
- 力量训练的“开始本组 / 完成本组 / 开始下一组 / 下一个动作”位于长滚动内容中，单手和训练中场景容易漏点。
- 有氧的“现在开始”和“补录已完成”混在同一张长表单，且实时模式预填较高坡度，存在误录与错误估算风险。
- 有氧没有暂停/继续，等器械、喝水或接电话都会进入有效运动时间。
- 设备状态在训练页不够直接，实时数据断开后恢复入口不够近。

### 2.3 综合运动能力缺口

- 现有 `CardioModality` 不应承载球类、攀岩和登山等不同语义。
- 现有实时样本缺少海拔/累计爬升等户外运动字段。
- 当前 Watch 活动类型映射缺少七项新运动。
- 当前静态 capability 会展示部分实际上没有采集实现的字段；2.0 必须由“运动类型 + 环境 + 当前传感器 + 实际样本”动态决定展示。

## 3. 方案选择

### 3.1 采用：独立综合运动领域，共享采集基础设施

新增 `SportKind`、`SportSessionDraft`、`SportSessionRecord` 和 `SportAnalysisEngine`。力量、传统有氧和综合运动保持各自记录语义，但共享：

- `LiveSensorCoordinator` 的唯一实时心率来源；
- iPhone 的定位与计步采集；
- Apple Watch workout session 和数据回传；
- `WorkoutMetricSample`、来源与可信度；
- Live Activity；
- 15 秒 checkpoint、后台强制保存和结束 flush；
- 统一历史和导出。

### 3.2 不采用：把七项运动直接加入 CardioModality

该方案会把球类、攀岩路线和户外海拔都压入有氧字段，导致 capability、能量、历史和训练效果语义混乱。

### 3.3 不采用：一次性重写整个 AppStore

全面拆分所有 store 会给 1.x 数据迁移和真机稳定性带来不必要风险。2.0 只抽取收益明确的持久化、运动分析和历史查询边界；`AppStore` 继续作为 SwiftUI facade，后续版本再逐步细分。

## 4. 导航与信息架构

底部保持五个直接入口：

1. **今天**：未完成训练恢复、下一步快捷操作、快速恢复打卡、今日训练和能量概览。
2. **计划**：力量/有氧计划、动作编排、动作库和算法依据。
3. **运动**：七项综合运动的最近项目、分类入口、实时开始和运动记录摘要。
4. **记录**：默认直接显示力量、有氧和综合运动的统一时间线；顶部提供近 30 天趋势入口。
5. **我的**：目标、身体参数、设备、健康权限、安全、导出和回收站。

Root 继续用全屏训练层保证未完成会话优先恢复，但把运动 draft 纳入同一互斥规则：同一时刻只能存在力量、有氧或综合运动中的一场活动会话。

### 4.1 今天页

页面首屏按优先级展示：

1. 未完成训练的“继续”卡；没有草稿时展示“开始今日力量 / 开始实时有氧 / 记录一项运动”快捷操作。
2. 精简恢复评分；详细四维输入可展开，保存与开训时均原子提交。
3. 今日能量和计划内容。

“开始今日力量”必须在同一 Store 操作中提交当前 `ReadinessInput` 与 `RecoveryCheckIn`，再创建训练草稿，确保页面分数、建议重量和实际训练使用同一份数据。

### 4.2 记录页

- 筛选支持：全部、力量、有氧、运动。
- 搜索支持训练名称、动作名称和运动名称。
- 整行点击进入详情；运动详情显示时间线、心率、距离/爬升、能量、负荷、恢复和数据来源。
- 继续保留回收站语义；运动记录也可以移入回收站、恢复和永久删除。
- 统一历史使用一次性查询快照，不在每次 SwiftUI body 重绘时重新扫描全部历史。

## 5. 实时训练交互升级

### 5.1 力量训练固定主操作

训练页面使用 `safeAreaInset(edge: .bottom)` 固定唯一主按钮。按钮随状态显示：

- 准备阶段：`开始本组`；
- 进行阶段：`完成本组`；
- 休息阶段：`开始下一组`；
- 动作完成：`下一个动作` 或 `完成训练`。

内容区继续允许直接修改重量、次数、RIR、动作质量和疼痛，但主循环无需滚动到底部。所有核心点击区域至少 44×44 pt。

暂停时显示明确遮罩、累计暂停信息和唯一“继续训练”按钮；暂停期间不能无意修改组状态。

### 5.2 休息提醒

- 保留灵动岛倒计时和展开后的“开始下一组”。
- App 前台在建议休息到点时提供一次触觉反馈；同一组只触发一次。
- 触觉和 Live Activity 只提醒，不自动开始下一组。

### 5.3 有氧入口与会话

有氧入口先分为：

- `现在开始实时记录`：选择项目和强度后开始，机器速度、坡度和功率默认为空/0；
- `补录已完成训练`：单独表单录入时长和实际可得指标。

实时页面固定底部显示暂停/继续和结束。有效时长排除暂停区间；能量、负荷和配速均使用有效时长。坡度、功率、器械校准等低频输入放入“调整负荷”区域，不阻挡实时指标。

## 6. 综合运动领域

### 6.1 运动类型

`SportKind` 包含：

- `badminton`：羽毛球；
- `tableTennis`：乒乓球；
- `soccer`：足球；
- `climbing`：攀岩；
- `hiking`：徒步；
- `mountaineering`：登山；
- `trailRunning`：越野跑。

分类为球类、攀爬、户外耐力。每个项目提供标题、SF Symbol、默认环境、可选环境、Apple Watch activity 字符串、MET 范围和 capability。

### 6.2 会话模型

`SportSessionDraft` 至少保存：

- 唯一 session ID、运动类型、室内/户外环境；
- 开始时间、更新时间、暂停区间和当前暂停时间；
- 原始 `WorkoutMetricSample`；
- 最新心率、平均/最大心率、累计距离、步数、步频和累计爬升的增量聚合；
- 数据缺口与来源；
- 15 秒 checkpoint 状态。

`SportSessionRecord` 至少保存：

- 开始/结束/有效时长、完成状态；
- 距离、步数、步频、累计爬升、平均/最大心率；
- session-RPE；
- 主动能量区间、训练负荷、心率区间、恢复区间；
- 原始样本、算法版本、来源、覆盖率和警告；
- 总结与后续 HealthKit 修订信息。

### 6.3 动态 capability

界面只展示当前确实可用或可合理推导的指标：

| 运动 | 手机实时能力 | Apple Watch/BLE 补充 | 明确不自动生成 |
|---|---|---|---|
| 羽毛球 | 时长；手机贴身时步数/步频 | 心率、设备能量 | 击球数、球速、回合、比分 |
| 乒乓球 | 时长；有限步数 | 心率、设备能量 | 击球数、球速、回合、比分 |
| 足球 | 户外距离、速度、步数/步频 | 心率、设备能量 | 触球、精确冲刺次数 |
| 攀岩 | 时长；户外合格定位时海拔/爬升 | 心率、设备能量 | 抓点、路线难度、自动完攀 |
| 徒步 | 距离、配速、步数、海拔、爬升 | 心率、设备能量 | 医疗风险与天气安全诊断 |
| 登山 | 距离、移动时间、海拔、爬升 | 心率、设备能量 | 高反诊断、技术难度 |
| 越野跑 | 距离、配速、步频、海拔、爬升 | 心率、设备能量 | 无合格 GPS 时的冲刺/坡度精度 |

华为健康不作为实时来源；若其样本事后写入 Apple 健康，则保留为独立来源并修订总结，不能与本机或 Apple Watch 数据重复相加。

### 6.4 Apple Watch 映射

- 羽毛球 → `.badminton` / indoor；
- 乒乓球 → `.tableTennis` / indoor；
- 足球 → `.soccer` / 用户选择 indoor 或 outdoor；
- 攀岩 → `.climbing` / 用户选择环境；
- 徒步 → `.hiking` / outdoor；
- 登山 → `.hiking` / outdoor，FitTune 保留 mountaineering 子类型；
- 越野跑 → `.running` / outdoor，FitTune 保留 trailRunning 子类型。

没有 Apple Watch 时，iPhone 与蓝牙心率路径必须完整可用。Watch 权限或启动失败只降低数据能力，不阻止会话。

## 7. 科学分析

### 7.1 能量

综合运动使用 2024 Adult Compendium 的运动特异 MET 范围作为手机估算先验，计算净主动能量：

`active kcal = max(MET - 1, 0) × 3.5 × weightKg / 200 × activeMinutes`

典型区间依据包括：

- 羽毛球社交/比赛约 5.5–9.0 MET；
- 乒乓球约 4.0 MET，强度不确定时扩大范围；
- 足球休闲/比赛约 7.0–9.5 MET；
- 攀岩低中难度/一般/抱石约 5.8–8.8 MET；
- 徒步约 3.8–7.8 MET，结合速度、负重和坡度只做区间修正；
- 登山约 6.0–10.3 MET，不能用海拔直接伪造精确代谢；
- 越野跑以越野/自选跑约 9.3–10.5 MET 为基础，并在配速和坡度数据合格时调整范围。

若有 Apple Watch 累计主动能量，只显示为“设备估算对照”或在缺少其他证据时作为宽区间中心；不标为直接生理实测，也不与 FitTune 估算相加。

### 7.2 心率与负荷

- 有可靠静息/最大心率时使用 HRR 区间；缺少静息心率时使用独立的 `%HRmax` 阈值并降低可信度，不能复用 HRR 阈值。
- 心率样本间隔超过 15 秒的时间不进入区间积分。
- session-RPE 负荷使用 `有效分钟 × session-RPE(1–10)`，作为同一用户纵向比较的任意单位，不代表生理损伤。
- 间歇性球类、足球和攀岩不显示整场心率漂移。
- VO₂max 不从球类、攀岩或任意一次综合运动自行估算；只能显示可识别设备已提供的估计及原始来源。

### 7.3 恢复建议

恢复以低精度范围显示，输入为有效时长、session-RPE、心率区间负荷、运动类型、当日恢复和数据覆盖率。范围只提供计划参考，不自动禁止下一次运动。

## 8. 传感器与后台生命周期

- Apple Watch 或 BLE 仍只占用一个实时心率槽位；iPhone GPS/计步可与其同时工作。
- 训练结束时新增“停止本次采集但保留首选设备”的 API，必须停止扫描、通知和自动重连，不能删除用户首选设备。
- `MotionLocationSource` 使用幂等 begin/end，并在视图消失时兜底停止。
- 户外运动才启动后台定位；室内球类不申请或启动 GPS。
- 海拔必须要求有效 vertical accuracy，并经过最小变化阈值过滤后累计爬升；无合格数据时显示不可用。
- 用户强制结束 App 时无法保证 iPhone 继续采集；恢复后明确记录 gap，不插值伪造连续数据。

## 9. 持久化与性能架构

### 9.1 SnapshotRepository

新增 `SnapshotRepository` 边界：

- 测试继续使用同步 `UserDefaultsSnapshotRepository`；
- 真机默认使用 Application Support 中的原子 JSON 文件；
- 首次启动从旧 `FitTune.snapshot.v1` 自动迁移；
- 每次成功覆盖前保留 last-known-good 备份；
- 主文件解码失败时尝试备份，并向 Store 暴露恢复提示；
- 设备首选项等小设置仍可留在 UserDefaults。

### 9.2 实时 checkpoint

- 力量、有氧和综合运动的连续传感器样本最多每 15 秒写一次完整 checkpoint。
- 开始、暂停、继续、完成一组、切换动作、进入后台、保存结束和放弃时立即保存。
- 会话内维护样本 ID 集合和最新聚合值，追加/查重为近似 O(1)。
- 页面读取最新聚合值，不再为每次渲染扫描全部样本。

### 9.3 查询快照与 Live Activity

- 统一历史建立一次性 `HistoryBrowserSnapshot`，搜索输入采用可取消防抖。
- 今日能量在同一 body 中只计算一次报告。
- Live Activity 对相同状态不更新；连续变化合并，更新频率不超过 1 Hz。
- strength/cardio/sport 会话结束、保存结束、放弃和 App 启动 reconciliation 均立即清理对应活动。

## 10. 数据迁移、去重与导出

- `AppSnapshot.currentSchemaVersion = 16`，新增运动记录、运动回收站和活动运动草稿均为 optional/default 字段，旧 JSON 可直接解码。
- 旧力量和有氧记录不被重算或改写。
- 实时样本以 session ID、来源、样本 ID/序号去重；累计能量按来源保持单调并在最终数据到达时替换，不相加。
- HealthKit workout 优先按稳定外部 UUID 或 FitTune session ID 合并；模糊时间匹配不得自动合并同日两场真实运动。
- JSON 完整备份包含运动记录和草稿；CSV 新增 `sports.csv`，指标 CSV 包含运动时序。
- 今日总消耗有 HealthKit 全天主动能量时继续以“静息 + 全天主动”为总值，运动记录只解释构成；没有全天主动能量时才合并互不重叠的力量、有氧、运动和日常步数估算。

## 11. 错误处理与降级

- 任一传感器、健康权限或设备缺失时不阻止训练。
- 持久化编码/写入失败不再静默；Store 保存最后错误，并继续保留内存草稿和 last-known-good 文件。
- Watch 启动失败、BLE 断开、GPS 权限缺失、定位精度差和海拔无效均显示当前降级来源。
- 运动总结只呈现实际满足 capability 的字段；缺失值显示“不可用”及原因，不显示 0 或虚假估算。
- 完成训练与总结展示按顺序切换，避免全屏层 dismiss 与 summary sheet 同时竞争。

## 12. 验收与测试

### 12.1 自动化

- 旧 schema 15 fixture 迁移到 16 后记录与草稿不丢失。
- 主快照损坏时成功从 backup 恢复；两者都损坏时暴露错误而非静默重置。
- 模拟高频样本证明有氧/运动 checkpoint 不超过每 15 秒一次，后台和结束立即 flush。
- 样本重复、乱序、累计值回退、15 秒心率 gap 和 session 不匹配均有测试。
- 七种 `SportKind` 的环境、能力和 Watch 类型映射有固定案例。
- MET 能量、session-RPE 负荷、有效时长、HRR/%HRmax 区间和恢复范围有基准测试。
- 暂停区间不进入有氧/运动有效时长、距离速度和训练负荷。
- 室内羽毛球/乒乓球不展示 GPS 距离，室内攀岩不生成虚假爬升。
- 统一历史搜索覆盖力量、有氧、运动和快速连续查询。
- Live Activity 相同快照不重复更新，且结束后立即清理。
- 当前未单独保存的恢复输入在开始力量训练时成为算法实际输入。

### 12.2 构建与真机

- 完整 Swift 测试零失败。
- iOS Simulator Debug 构建、Release 真机签名构建、Watch target 和 Widget target 均成功。

- 无 Apple Watch 的情况下验证 iPhone-only 和 HUAWEI WATCH FIT 3 BLE 心率广播路径；Watch 特定实时能力以编译、协议测试和未来配对真机测试为验收边界。

### 12.3 产品指标

- 从“今天”首屏开始计划力量训练不超过 2 次点按。
- 训练主要操作无需滚动，所有主要控件至少 44 pt。
- 运动板块到开始任一运动不超过 2 次点按。
- 60 分钟 1 Hz 会话的持久化次数不超过周期 checkpoint 加生命周期事件。
- 相同 Live Activity state 不产生更新；连续更新不超过 1 Hz。
- 会话结束后 1 秒内停止定位、计步和实时心率采集状态。

## 13. 依据与限制

- Apple HealthKit workout session、activity type、Core Location 和 Core Motion 能力按 Apple 官方文档实现；后台能力不承诺覆盖用户强制结束 App。
- 运动能量依据 2024 Adult Compendium（Herrmann 等，J Sport Health Sci. 2024;13:6–12，DOI `10.1016/j.jshs.2023.10.010`）。
- session-RPE 使用 Foster 等提出的有效分钟 × RPE 方法（PMID 11708692），只作个人纵向内部负荷指标。
- GPS 距离、海拔、腕表能量、心率公式和恢复范围均存在个体与设备误差；FitTune 必须展示来源、覆盖率和限制。
