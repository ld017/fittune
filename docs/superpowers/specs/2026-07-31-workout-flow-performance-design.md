# FitTune 训练流程与性能修复设计

日期：2026-07-31

## 目标

修复力量训练中的三类问题：

1. “个人心率恢复历史不足”等实时建议原因随心率刷新重复追加。
2. 休息结束后需要先点“准备下一组”、再点“开始本组”，容易漏记组开始时间。
3. 动作替换、计划编辑和动作搜索卡顿，训练中持续采样时内存与持久化开销过高。

## 已确认根因

- 实时适配把已经包含心率说明的 `recommendation.reason` 再次作为基础原因，每次心率响应变化都会继续拼接相同文本；休息原因与决策日志也可能重复增长。
- `advanceDraftToNextSet` 只结束休息并进入 `.training`，开始计时还依赖第二次操作。
- `ExerciseReplacementView` 的排名、筛选、肌群/模式分组和历史重量迁移均为计算属性；一次 SwiftUI 重绘会重复扫描目录与训练历史，搜索每输入一个字符都会放大计算量。
- 每个实时心率样本都会重新扫描样本数组并把完整 `AppSnapshot` 编码写入 `UserDefaults`，训练历史越多，开销越大。

## 设计

### 1. 心率建议保持幂等

- 实时适配输出结构化、去重后的原因列表。
- 既有原因按分隔符拆分后去重；动态心率原因只保留当前状态的一条。
- 休息原因与心率决策事件按语义去重，不因同一恢复状态的连续样本无限增长。
- UI 仍显示“历史不足”，但只显示一次；数据不足只降低可信度，不阻塞下一组。

### 2. 一次点击真正开始下一组

- 新增原子操作 `startNextDraftSet`：同一时间点结束休息、进入下一组、应用建议输入、写入本组开始时间并切换到 `.setActive`。
- 休息卡主按钮改为“开始下一组”，一次点击即开始计时。
- Live Activity 的“开始下一组”使用同一原子操作。
- 不采用倒计时结束后自动开组，避免用户尚未准备好时产生错误训练记录。
- 初次进入动作仍保留“开始本组”；所有建议重量在组开始后仍可手动修改。

### 3. 动作替换与搜索性能

- 将目录排名、筛选、分组和重量迁移结果构建为一次性的浏览快照。
- 搜索输入采用短延迟且可取消的刷新；旧查询不得覆盖新查询。
- SwiftUI `body` 只渲染快照，不再为每个分区、动作和重绘重复扫描全目录。
- 最近动作与最近重量预先建立索引，候选行不再逐条排序完整训练历史。
- 选择、收藏或筛选变化时只重建必要快照。

### 4. 实时采样与持久化

- 心率样本仍完整保存在当前训练草稿中，保证总结和断点恢复。
- 平均心率采用增量统计，避免每个样本重复遍历全部历史样本。
- 实时样本更新继续驱动当前心率与恢复建议，但完整快照按固定最短间隔批量持久化。
- 完成一组、进入后台、暂停、结束或放弃训练时仍立即保存，不降低断点保护。
- 决策日志只在建议状态发生实际变化时追加。

## 安全与兼容

- 不自动增加重量、不自动结束动作、不自动开始下一组。
- 旧训练草稿和历史记录继续解码；新增统计字段使用可选值或可重建默认值。
- 同 Bundle ID 覆盖安装，不卸载、不清除数据。

## 验证

- 回归测试证明连续相同心率状态不会扩大建议文本或日志。
- 生命周期测试证明一次点击从休息直接进入计时中的下一组，并保留用户可编辑输入。
- 搜索快照测试覆盖快速连续查询、筛选、收藏优先和历史重量索引。
- 持久化测试证明实时采样受到节流，而关键生命周期事件立即保存。
- 运行完整 Swift 测试、iOS Simulator 构建，并在真机覆盖安装后启动确认。
